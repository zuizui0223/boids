# v176 真正2016年ラベルのDEMと測量元isourceを同じ画素で検証

2026年11月17日。v169の本物のRWS Vlieland Haven港潮位（水位高さ）による2018学習→2019保留ミヤコドリACC行動分類の予測増分は+0.007430798 MSEだった。ただし**実際の干潟標高×鳥GPS地点による局所アクセス機構**は未検証。地形SOURCEの長い取得作業で、v170ではBorndiep誤地域の2016/2019ファイルをSOURCE_STOPし、v171–v173で公式165タイルから地理的にVlieland周辺と交わる10枚を確認、v174で10枚に\`z,time,isource,x,y,crs\`があり元EPSG:28992ということを実測。v175では**10枚すべてでnative timeが2016-01-01という年ラベルの層を一つずつ含み、その同じ層の\`z\`と\`isource\`は(time,y,x)3次元格子**と確認した。

## 結果前に固定した新SOURCEセル監査

1. v175の10枚の真正\`time\`全値／元ラベル\`2016-01-01\`のインデックスと、v174の元DDS/DAS SHA付き元URLを完全再照合した後、当該タイルの**2016年ラベル1時刻の\`z\`と\`isource\`のみ**をOPeNDAPから取得する。各tileは元の約625×500セルの単一時刻のみ、歴史地形の全時間配列を取得しない。
2. 元の\`_FillValue\`マスクを保持し、zの数値を浮動へ変換した上でNaN/原フィル値/著しく不自然な大きな値を欠測として除外。**測量データが無いこととz=0mを厳密に区別**。SOURCE\`z\`の単位は元DDSでmと確認済み、地理はEPSG:28992であることを再チェックする。
3. 同じ\`time,y,x\`位置の原\`isource\`は元測量ソースファイルのゼロ始まりindexであり、鳥IDや測量「日付」ではない。元の有効zセルのうち\`isource\`が同じ画素に有効な割合、SOURCEコードの区分ごとの画素数を集計する。元DEM全画素値はGitHubに保存しない。
4. **非欠測のzセル≥1,000/タイル**なら、次のGPS点対応SOURCE候補としてのみ入場させる。1,000未満やオリジナル配信停止ならタイルはSOURCE_STOP、0セルを「海がない」や「ミヤコドリが採餌しない」と読まない。
5. 2016年のtime座標が\`2016-01-01\`でも、この時刻は年次の代表ラベルであって同日測量の証拠ではない。また2016レイヤーが合成・継承された画素である可能性がある。**元\`isource\`と元出典の対応・地形測量日が証明されるまで、各ピクセルの真の測量年は未確定**。
6. 元RWS港水位と元DEMの\`m\`が**同じ垂直NAP高度基準**だとまだ検証できない。したがって\`h_{\mathrm{harbor}}-z_{\mathrm{DEM}}\`を「GPS地点の水深」と呼ばず、冠水・干潟アクセス量を推定しない。

## 出力と限界

全10の候補タイルについて2016年ラベルの\`z\`非欠測セル数/母数、元isource両方有効な画素数、zの広域分布要約、測量ソースインデックスごとの画素数、SOURCE STOP状態を保存。元の格子高度、動物GPS/ACC、港実測潮位配列をGitHubへ転載しない。

科学的SOURCEの次段：2016（または2017）の実有効な地形と同じ鳥の2018/19元GPSをEPSG:28992へ正しく変換し、鳥が実際に記録された有効なDEMセル比率を測る。そこで当時の地形の出典／同じNAP垂直基準が確認できた場合だけ、**局所干潟干出面積・行動に対する物理アクセス予測**へ進む。潮汐×太陽因果交互作用や個体間Boidsの運動力は依然未推定。
