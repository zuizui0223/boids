# v175：Vlielandの歴史的NetCDFの原測量時刻を直接読み、実際に2016年の層があるか確認する

2026年11月17日。次に必要な機構は、実GPS点における当時の干潟標高とRWS港湾水位を対応させ、潮位の高さによる採餌ACC分類予測情報が**干潟アクセス可能性**と結びつくか検証すること。v169では水位高さ1項が、真の2018年学習→2019年全年保留で元RWS潮位5項のMSE改善の約98.3%を占めたが、位相固有性は弱かった。

## 元SOURCE入場と誤りを防ぐ条件

前段v173は公式Deltares索引165タイルの座標と\`timeCoverage\`から、Vlieland広域と重なる10候補を固定。v174ではその10個のOPeNDAP\`DDS\`/\`DAS\`の**本物のprovider原レスポンス**を取得し、全10タイルに\`z,time,isource,x,y,crs\`があり、時間層が8〜39であることをSHAとともに再現した。

**しかし**NetCDFのカタログ\`timeCoverage\`が2016年を挟むことは、元NetCDFの実際の\`time\`座標に2016年があり、その時刻の\`z\`に有効標高セルがあることと異なる。そこでv175は初めて、10タイル各々の**本物の\`time\`座標の数値だけ**をOPeNDAPから読んで元の実カレンダー年を復元する。単位は元DDS/DASで確認した\`days since 1970-01-01\`。可能なら\`isource\`の各時刻での元調査源コードも読み、元sourceが異なる測量を区別する。データ本体の\`z\`全格子や実GPS点は一切取得しない。

### 今回の固定SOURCE判定

1. v174の真正10タイルSOURCE元DDS/DAS SHAレシートが存在し、すべて\`time/isource/z\`を原プロバイダが持つことを確認。
2. 本物のremote OPeNDAP datasetから1次元の\`time\`全値（各8〜39値）だけ取得し、元DDSのtime配列数と一致。元source日付を\`YYYY-MM-DD\`へ変換して全件保存。もしnetCDF4のリモートアクセスが失敗すれば、同じ公式OPeNDAPの小さな \`.ascii?time\`応答を元構文で厳密に読み取れる場合だけ許可し、受信値SHAも保存。成功しなければ**SOURCE STOP**。カタログの開始／終了日を測量時刻として代用しない。
3. タイルごとに**2016年の実timeエントリ数とタイムインデックス**を保存し、さらに2018年以前・2019年以前の最も新しい測量日を記録。2018/19年の鳥行動より**未来の測量層を過去の標高として使用しない**。
4. 実timeに2016年があっても\`z\`に有効な2016年標高があるかは未確認、また鳥の実GPS地点を覆うことも未確認。物理的干潟アクセスはSOURCE入場に不可。
5. 元地点別GPS/ACC元時刻、個体ID、元RWS時刻別潮位、DEM全標高配列はユーザーの公開GitHubリポに転載しない。

本SOURCE-only段階の結果によって、「時刻をもつ2016年の生標高zを次段でサンプルしてよい原タイル」だけに減らせる。もし一部タイルには2016年の真の時刻が存在しないなら、カタログに2016年が入っているだけでは年次の物理的機構を主張できないという反証として保存する。

実行：\`python -m unittest discover -s validation_v175 -p 'test_*.py' -v\`、\`python validation_v175/native_actual_survey_time_source.py --emit\`。結果を固定したら\`--check\`で元true time座標全値と元SHA（ASCII時はproviderレスポンスSHA）を再計算。
