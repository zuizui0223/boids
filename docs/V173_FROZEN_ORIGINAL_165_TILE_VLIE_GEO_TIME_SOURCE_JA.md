# v173：Vlielandの歴史的干潟地形を公式Deltares 165タイル索引の座標・時間で絞る

2026-11-17。v170ではRijkswaterstaat/Deltares OpenEarthの2016年・2019年元NetCDFを実際に取得したが、資料中の元sourceがBorndiepであり、Vlielandの候補範囲と地理的に交わらず、鳥のGPSに結合できない**SOURCE STOP**だった。v171で正式THREDDS XMLに166個の元NetCDF path（1つは\`catalog.nc\`）、v172では本物の\`catalog.nc\` 40,976 bytesをSHA256 \`b4364e1d18ea3098ccef8fcbd9a9f3506e98264748c0fe9ce80697a9cb9a2193\`で検証した。

## 本当の情報が入った165タイル座標索引

公式NetCDFには、**165件**のURL、実投影地理\`projectionCoverage_x/y\`各165×2、WGS84の\`geospatialCoverage_eastwest/northsouth\`各165×2、さらに\`timeCoverage\`165×2（原属性\`days since 1970-01-01\`）が対応している。元カタログの作成日は2026年3月で、各元タイルの全地形測量日とは異なる。

本v173では、**新たな生物の予測値を一切見ず**、元NetCDFの165タイルのURLとRD New投影x/y、WGS84、タイムカバレッジを揃えて、Vlieland周辺の粗いSOURCE検索窓\`x=120,000–150,000m、y=575,000–615,000m\`と重なるタイルを特定する。これは原2018/19鳥GPS個別地点の地理的範囲ではなく、タイル候補を網羅的に発見するための大きめの窓である。元インデックスに2016/2018/2019年が\`timeCoverage\`として含まれる場合だけ年候補に印を付ける。**カタログのタイムレンジ内に2016年がある≠各ピクセルの実測年が2016年である**。特定の地形年に使える有効なzと\`isource\`、NAP基準の確認は次段へ残す。

ソースだけの入場条件：元正式\`catalog.nc\`を再取得し、バイト数40,976とバイトSHA完全一致、URL/地理/時刻フィールドが165行の完全配列であることを確認。毎タイルのURL、元WGS84/RD New bbox、交差面積、収録タイムレンジを公開可能なSOURCE-safe JSONに記録。ゼロ交差ならSOURCE STOPし、都合のよい地形を代用しない。

## 今回はまだしないこと

- 元GPS個体の位置を公開したり、特定の鳥が原DEM上のどのセルにいるかを調べること。
- 元2016年前後の同一DEM測量者・空白セル・古いセルと新しいセルの地形を平均したり、未来の2025年地形を2018年へ使うこと。
- 2018/19年元RWS港の実測水位を干潟上の現地水位と見なし、実際の採餌可能面積や魚／鳥の因果効果を計算すること。

本版は、次段で元の2016-2019年測量を含む**本当のVlieland地理タイルをsource-date-awareに読めるか**のための入場。v169の鳥ACC分類源での潮位高さの追加予測情報は既に再現したが、地形によりその機構が示されたわけではない。

コード：\`validation_v173/historical_vlieland_tile_shortlist.py\`。初回\`--emit\`で元公式索引を再取得して、匿名SOURCEだけを凍結。その後\`--check\`へ移行し、元バイト・座標・年範囲の完全再現を要求する。

**局所干潟の実GPSと歴史的測量標高の対応、Boids個体間相互作用、因果的な潮汐×太陽効果は未推定。**
